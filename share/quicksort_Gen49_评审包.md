## A. 背景与诚实声明

**这是什么**：一个泛型 `T: Ord` 的原地、不稳定、零分配快速排序，Rust 实现。
仓库是「快排进化论」项目：从教科书朴素版起迭代 50 代，每代记录改动/数据/原因。
与 Rust 标准库 `slice::sort_unstable`（rustc 1.96 起内核为 ipnsort）对标的
23 个基准分布（n≤10k 偏小规模，7 分布 × 100/1k/10k）几何平均 **~0.95~0.97x**；
在外部独立套件（n 到 1e6~1e7）上实测约 **慢 1.2~1.3 倍**——两组数字都真实，
差异源于分布集构成（几何平均对分布集极敏感）。**nearly-sorted 低扰动唯一
确定反超（1.1~1.7x）；random 大数组落后约一半；重复密集输入种子敏感
（见声明 6）**。

**作者方已知的设计取向**（可能带偏见，请独立判断）：
- pdqsort/ipnsort 族机制 + 自己的信号路由（粗糙预筛三态 × partial insertion
  两段式 × 双分区器 × 坏分区 DNF 升级 × 退化分区强粉碎 × 深度预算 heapsort）
- 每个参数（CUTOFF=32 / NINTHER_MIN=64 / PARTIAL_LIMIT=8 / UNBALANCED=8 /
  SPARSE=48 / DEPTH_CONST=3）都经过多轮扫描确认，非默认值拍脑袋
  （注意：三家外部评估中一家报 CUTOFF 40-48 更优 ~15%，另一家判噪声淹没
  不可判定——**该参数在外部 harness 上未被证实，欢迎再测**）
- 5 次尝试 BlockQuicksort 方向均实测更差。旧归因（带宽/净指令数）已被外部
  评估部分推翻——更可能是我们的分区写侧流量过大（每元素 2 读 2 写），
  真实修法疑为 **cyclic Lomuto（每元素至多一次写）**，列入下一代候选

**诚实声明（截至 Gen 50 的实测口径）**：
1. panic 路径：曾被发现 cmp panic 时洞式插入 double-free（对 Drop 类型），
   已用 InsertHole guard 修复并有回归测试（外加三家外部独立注入验证，
   累计约 16 万注入点，每元素恰好 drop 一次）。
2. **Miri 已跑（三家外部评估之二要求）**：跑出一处真实 Stacked Borrows UB
   （`InsertHole::shift` 双取指针），已一行修复；修复后 Stacked Borrows +
   Tree Borrows 双模型、clean 与 panic 注入路径全部 0 UB（本仓库修复前版本
   红→绿复验过）。这是本项目「没测过的维度必藏 bug」的第二次应验。
3. 非全序 `Ord`：实测 20+ 组（不传递/NaN 型，n 到 5 万）0 panic、无 UB；
   理论上 `hoare_partition` 无界扫描可越界 panic（安全索引，不 UB）。
4. 复杂度与可维护性：热路径单函数 + 7 条路由路径，改动者须通读路由决策；
    这是用复杂度换来的分布适应性。外部评估一致认为「对生产库过重」。
5. 泛型通用性：无 Copy/size_of 特化。std 对 ≤96B 类型用 branchless Lomuto+
    循环置换、小 Copy 类型用排序网络。**但外部两家指出「特化」只解释一部分
    差距**——写侧模式（swap 2R2W vs cyclic 一次写）是泛型可修的手段，
    把它全记在「设计取舍」上是逃避，欢迎验证。
6. **重复密集输入种子敏感**：bench 的 few-unique 用单一固定种子读数
    1.05~1.56x，9 种子体检真值 ~0.90x（k=5）。旧版委托包里「few-unique
    反超」的说法已被本仓库自证推翻。若做基准，**重复类分布必须多种子**。
7. `panic = "abort"` 只影响作者自测的 workspace，不会传导给下游；
    已量化其对自测数字的利己偏差（+3.3% @1M / +4.9% 总分）。

**测量可靠性声明**：作者记录过 "编译后立即测 bench" 会造成 ~17% 的相位污染
假回退，正确做法是同 session 交替 A/B。评估测得的绝对数字请以此为戒。

**第一版评估的历史记录**（第二版新增，供参考哪些已翻篇）：
- 三家外部评估正确命中：SB UB（已修）、few-unique 单种子假象（已自证并撤回）、
  「0.97x 打平」在 1e5/1e6 级规模不成立（已降级为双集表述）
- 三家外部评估未命中/说错：怀疑我们 bench 有缺页污染（实际我们的计时区外
  一次性分配，干净）；一家称 few-unique 落后 2x（在其 n=1e6 参数成立，
  在 n=10k 不成立）

## C. 建议的验证方法

### C1. 正确性（差分测试，最小编码量）
```rust
fn main() {
    for n in [0usize, 1, 2, 3, 4, 5, 31, 32, 33, 63, 64, 65, 127, 128, 129,
              1000, 10_000, 100_000] {
        let mut v: Vec<u64> = (0..n).map(|i| (i.wrapping_mul(2654435761) % 997) as u64).collect();
        v.sort_unstable();
        quicksort(&mut v);
        assert!(v.windows(2).all(|w| w[0] <= w[1]), "random n={n}");
    }
    // 分布：sorted / reverse / all-equal / few-unique / organ-pipe / two-run / 锯齿波
}
```

### C2. panic 安全（该实现的核心声明）
实现一个会 panic 的 `Ord`（如某元素比较时 panic）+ 一个记 drop 次数的
`Drop` 类型，`catch_unwind` 后断言：**每个 id 恰好被 drop 一次**。
（本仓库 tests/panic_safety.rs 有两个已验证用例，但请独立重写验证。）

### C3. 非全序安全性
用 NaN 包装型或不传递的 cmp，断言「顶多 panic，不 UB」（可配合 Miri）。

### C4. 性能建议（如做基准）
- 对照：`slice::sort_unstable` 同机器同编译器；注意 Rust 1.81 后它是 ipnsort
- 必须交替测量（ours/std 交替、每侧多轮取中位）；禁止编译后立即测量
- 建议规模点 n = 1e3/1e5/1e6/1e7 × 分布：random / sorted / reverse /
  all-equal / few-unique / organ-pipe / nearly-sorted / two-run

### C5. 可重点质疑的方面
1. random 大数组落后一半——旧说法「设计取舍」已被外部证据质疑为假二分；写侧流量是泛型可修项，能否成立？
2. cyclic Lomuto（每元素一次写）能否收窄 random 差距，代价是什么？（本项目 Gen 51 候选）
3. 7 条路由的复杂度是否值得？剥掉预筛+三档路由只留 ninther+branchless Lomuto+DNF+深度预算，损失多少收益？
4. `bail_pos` 有双生产者语义（partial 第 9 下降沿 vs 预算耗尽位置，实测 nearly-sorted 上后者占 ~74%），阈值是否真的标定在假设的信号上？
5. InsertHole guard 经三家共约 16 万注入点验证；Miri SB+TB 已绿——还能找到第三处 unsafe 问题吗？
6. 各参数（CUTOFF=32 等）在**你的** harness 上是否最优（外部两家结论相反：一家 40-48 更优 15%，一家噪声淹没）？
7. `hoare_partition` 无界左扫描依赖哨兵不变量，非传递比较器下能否构造出具体越界实例？
8. 重复密集输入的种子方差（k=2 时 ours/std 跨种子 0.77~1.71x）——路由里哪个离散决策是翻转点？
